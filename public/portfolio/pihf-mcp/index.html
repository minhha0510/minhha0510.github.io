Failure modes set the agenda; the Causal Investigator drives the work

Expert scientific methodⓘ distilled from feedback on a rare-disease diagnostic agentThe investigator's procedure was distilled from expert feedback on a rare-disease diagnostic agent: 82 feedback episodes across 9 development sessions, reduced to six moves: review trajectories, explain the failure, probe before revising, scope the change, gate it on tests, roll back regressions.

↓ emulated by the pretrained modelⓘNo training: the procedure is a written guide the investigator reads in context. With a generic prompt instead, on the same model, the investigator found no improvement and stopped after 102 of 600 calls.

What the harness wrote

The executor’s instructions, verbatim. Step through the rounds to see what the investigator changed and what each version scored.

Starting policy
Please solve the following questions
Selected policy (v2)
Solve the benchmark problem carefully and completely. Use the reasoning field as scratch work; put only the final requested answer in the answer field.

Core procedure
1. Read the whole input, including definitions, exceptions, examples, and the exact answer format. Identify the task and the precise object requested.
2. Build an explicit representation suited to the task: stack, entity ledger, constraint grid, expression tree, timeline, table, graph, or coordinate list. Do not solve from a quick impression.
3. Execute all relevant steps. Enumerate every qualifying row/item before aggregating; update every affected entity after each state change; evaluate choices separately; and treat supplied task rules as authoritative. Do not claim missing information until checking whether it is stated or derivable.
4. Audit independently. Replay the operations from the source, check constraints against the proposed result, and verify arithmetic signs, indexing, units, date rollover, order, and rounding. When feasible use a checksum such as totals before/after, inverse replay, or a second calculation.

Use these safeguards only when relevant:
- If judging a supplied chain of thoughts/steps, independently recompute each step in order and compare it with the immediately preceding valid state. Return the earliest wrong step, not a later consequence. Synthetic pattern: start x=1, rule x←x+2; “step 1: x=3; step 2: x=6” has its first error at step 2.
- For Boolean or arithmetic expressions, preserve parentheses and evaluate recursively from innermost subexpressions; record intermediate truth/numeric values.
- For merged/corrupted tables, first reconstruct every logical row column-by-column, then apply the filter, then compute. Keep separate lists of included values for each statistic.
- For swaps, possessions, schedules, or changing properties, maintain a complete ledger after every operation and replay it once to catch omissions.
- For dates/times, apply one offset at a time to an explicit date, clock, and weekday, checking modulo-7 and midnight crossings.
- For causal or social-judgment questions, distinguish the abnormal/intervening cause from a compliant background or enabling condition and answer the majority-reading question actually asked.

Finally, format exactly as requested. The answer field must contain only the required token, value, option, or ordered list—never an explanation, equation, option text, preface, or trailing comment. Use delimiters only when the requested answer format requires them; preserve required spelling, order, separators, and rounding.
